# DE-18 deployment and verification

Run DE-SECURITY-01 first and verify it using `supabase/verification/de-security-01.md`.
The DE-18 migration aborts if its hardened grants, payment-table policies,
atomic invitation and trusted reconciliation RPCs, attestation, constraints, or immutability triggers are
missing. These commands have **not** been run against production.
The effective service-role payment contract is SELECT/INSERT only; excess
UPDATE/DELETE/TRUNCATE/TRIGGER/REFERENCES or column grants reject the prerequisite.
Inherited excess privileges require a separate review; do not change global
Supabase role inheritance to bypass the gate.

## Read-only preflight before migration

The repository does not contain production definitions of `get_user_tenant_id()` or `is_super_admin()`. The allocator checks `tenant_members` and `super_admins` directly, following the DE-19 application resolver. Before applying SQL, inspect those helper definitions and the deployed `tenant_members.permissions` type and values to confirm the live schema matches the reviewed contract:

```sql
SELECT n.nspname AS schema_name, p.proname AS function_name,
       pg_get_functiondef(p.oid) AS definition
FROM pg_proc AS p
JOIN pg_namespace AS n ON n.oid = p.pronamespace
WHERE p.proname IN ('get_user_tenant_id', 'is_super_admin')
ORDER BY n.nspname, p.proname;

SELECT column_name, data_type, udt_name
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'tenant_members'
  AND column_name IN ('tenant_id', 'user_id', 'role', 'permissions')
ORDER BY column_name;

SELECT role, permissions
FROM public.tenant_members
WHERE permissions IS NOT NULL
LIMIT 10;
```

Confirm that `user_id` and `tenant_id` are UUIDs, role values include `owner` and `staff`, and permissions use the DE-19 `sales`/`purchases` or `canViewSales`/`canViewPurchases` boolean overrides. If the live schema differs, revise and review the migration before applying it.

Also inspect every non-null tenant ID in `tenants`, `sales`, and `purchases`. The migration rejects any ID outside the four approved IDs, including a tenant with no surviving invoices. An unapproved tenant requires a verified historical high-water and a reviewed migration change before deployment.

## Deployment order and protected pause

1. Prepare the compatible server-route build and rehearse it in staging.
2. Pause all protected business writes: sale create/edit, purchase create/edit, member management writes, invitation issuance/acceptance, and all direct Data API writers.
3. Pause standalone customer/supplier payments and FIFO/status refresh requests. No old payment route or sale-origin automatic payment insert may run after payment-table write revocation.
4. Pause tenant creation and provisioning.
5. Drain in-flight requests for every paused workflow.
6. Quiesce or remove old app instances that use authenticated direct header, member, or payment writes, including count-based invoice routes.
7. Deploy the compatible server-route build while writes stay paused.
8. Apply `supabase/migrations/20260930000000_de_security_01_write_hardening.sql`.
9. Verify payment and header privileges, read-only policies, role constraints, identity triggers, atomic invitation acceptance and response-loss reconciliation, and trusted routes with the DE-SECURITY-01 runbook. Require effective service-role payment SELECT/INSERT only.
10. Re-run and approve the complete tenant roster and sale/purchase historical invoice high-water preflight. No new tenant may appear between this preflight and the DE-18 seed.
11. Apply `supabase/migrations/20260930000001_de18_invoice_counters.sql` once. A missing security prerequisite, unapproved tenant, or malformed tenant-scoped invoice aborts; investigate before retrying. Legacy `tenant_id IS NULL` rows are excluded.
12. Run the read-only counter checks below and verify allocator authorization. Confirm two rows per tenant and the approved historical minima.
13. Exercise controlled sale, purchase, member, invitation, customer payment, and supplier payment smoke tests, including FIFO statuses. The expected first numbers from the approved high-water snapshot are `SAL-0031` and `PUR-0007` for Doctors Egg, `SAL-0005` and `PUR-0005` for khubaib test, `SAL-0008` and `PUR-0004` for Testing, and `SAL-0002` and `PUR-0002` for Testing Haris. Newer pre-migration documents or verification allocations can make actual numbers higher.
14. Resume writes only after all checks pass and every old instance is gone.

The DE-18 migration locks `tenants`, `sales`, and `purchases` while seeding,
but the operational pause also covers payment, FIFO, member, invitation, and
provisioning requests outside those locks.

## Read-only checks after migration

```sql
SELECT t.id AS tenant_id, t.name, k.counter_type, c.last_number,
       CASE WHEN c.counter_type = 'sale' THEN 'SAL-' ELSE 'PUR-' END ||
         lpad((c.last_number + 1)::text,
              greatest(4, length((c.last_number + 1)::text)), '0') AS next_number
FROM public.tenants AS t
CROSS JOIN (VALUES ('sale'), ('purchase')) AS k(counter_type)
LEFT JOIN public.invoice_counters AS c
  ON c.tenant_id = t.id AND c.counter_type = k.counter_type
ORDER BY t.name, k.counter_type;

SELECT 'sale' AS counter_type, s.tenant_id,
       max(substring(s.invoice_number from 5)::numeric) AS surviving_max,
       c.last_number
FROM public.sales AS s
JOIN public.invoice_counters AS c
  ON c.tenant_id = s.tenant_id AND c.counter_type = 'sale'
WHERE s.tenant_id IS NOT NULL
GROUP BY s.tenant_id, c.last_number
HAVING max(substring(s.invoice_number from 5)::numeric) > c.last_number
UNION ALL
SELECT 'purchase', p.tenant_id,
       max(substring(p.invoice_number from 5)::numeric), c.last_number
FROM public.purchases AS p
JOIN public.invoice_counters AS c
  ON c.tenant_id = p.tenant_id AND c.counter_type = 'purchase'
WHERE p.tenant_id IS NOT NULL
GROUP BY p.tenant_id, c.last_number
HAVING max(substring(p.invoice_number from 5)::numeric) > c.last_number;

SELECT has_table_privilege('authenticated', 'public.invoice_counters', 'UPDATE') AS authenticated_can_update,
       has_table_privilege('authenticated', 'public.invoice_counters', 'DELETE') AS authenticated_can_delete,
       has_function_privilege('anon', 'public.allocate_invoice_number_v1(uuid,text)', 'EXECUTE') AS anon_can_allocate,
       has_function_privilege('authenticated', 'public.allocate_invoice_number_v1(uuid,text)', 'EXECUTE') AS authenticated_can_allocate,
       has_function_privilege('anon', 'public.allocate_invoice_number_trusted_v1(uuid,text)', 'EXECUTE') AS anon_can_call_trusted,
       has_function_privilege('authenticated', 'public.allocate_invoice_number_trusted_v1(uuid,text)', 'EXECUTE') AS authenticated_can_call_trusted,
       has_function_privilege('service_role', 'public.allocate_invoice_number_trusted_v1(uuid,text)', 'EXECUTE') AS service_role_can_call_trusted;
```

The first query must show two non-null rows per tenant. The second query must return zero rows. The seven privilege booleans must be `false, false, false, true, false, false, true`. Do not use the displayed next number as a reservation; it may change immediately under concurrency.

## Seed contract in disposable staging PostgreSQL

Before production activation, test the migration on fresh disposable copies of the relevant schema and data. With exactly the four approved tenant IDs, it must seed `GREATEST(approved, live numeric maximum)` for each kind. A fifth non-null tenant, even with no surviving invoices, must abort the migration; a `tenant_id IS NULL` legacy invoice must not affect it. Test a live maximum both above and below an approved minimum. A malformed tenant-scoped invoice must abort. After a successful migration, insert a new tenant and verify its sale and purchase counters both start at zero. Use a fresh copy for each migration scenario.

## Concurrency check in staging PostgreSQL

Use isolated staging tenants, authorized owner UUIDs, and two SQL sessions. Allocations consume numbers and must commit. Do not run these checks against production merely to test concurrency. In each session, substitute the UUIDs and run:

```sql
BEGIN;
SET LOCAL ROLE authenticated;
SELECT set_config('request.jwt.claim.sub', '<OWNER_USER_UUID>', true);
SELECT public.allocate_invoice_number_v1('<TENANT_UUID>'::uuid, 'sale');
```

**Same tenant, same type:** Read the sale row's starting `last_number` as `N`. Run session A through allocation and leave its transaction open. Start session B with the same tenant and `sale`; it must wait on that row. `COMMIT` A; B must then return the other number. `COMMIT` B. The two returned strings must be distinct and encode exactly `N+1` and `N+2` (order depends on which transaction won). Query `invoice_counters` after both commits: the sale row must be exactly `N+2`. No duplicate invoice string may have been returned. Repeat for `purchase`. If the SQL client times out instead of waiting, increase its staging statement timeout.

**Same tenant, different types:** Read sale `last_number = S` and purchase `last_number = P`. Leave a sale allocation transaction open in A, then allocate `purchase` in B. B must return without waiting for A's commit. Commit both. The returned values must encode `S+1` and `P+1` with their respective prefixes, and the stored rows must be exactly `S+1` and `P+1`.

**Different tenants, same type:** Read sale values `A` and `B` for two tenants. Leave tenant A's sale allocation open, then allocate tenant B's sale in the other session. The second must return without waiting for the first commit. Commit both. The stored rows must be exactly `A+1` and `B+1`; each tenant's returned string must match its own row. Strings may have the same numeric suffix across tenants because uniqueness is tenant-scoped.

Use this read-only query after each committed scenario, with the relevant tenant IDs:

```sql
SELECT tenant_id, counter_type, last_number
FROM public.invoice_counters
WHERE tenant_id IN ('<TENANT_A_UUID>'::uuid, '<TENANT_B_UUID>'::uuid)
ORDER BY tenant_id, counter_type;
```

**Authorization:** As `authenticated`, call the ordinary function with an owner and allowed staff member; sale and purchase must succeed for their tenant. Then test a user outside the tenant, a staff user with `sales`/`canViewSales` or `purchases`/`canViewPurchases` set to `false`, a malformed recognized permission, an unknown-role member, and a missing member. Each denial must leave `last_number` unchanged. A direct ordinary RPC by a super-admin must be denied even if that person has a membership row. `anon` must lack EXECUTE on both functions; `authenticated` must lack EXECUTE on the trusted function. An invalid `p_counter_type` must raise SQLSTATE `22023`.

**Selected super-admin route:** With a valid `?tenant_id=<TENANT_A_UUID>` and a super-admin session, create one sale and one purchase through their HTTP routes. The service-role-only trusted allocator must advance each selected row once. Retry without selection, with an invalid ID, and with a nonexistent ID; every request must fail before either counter changes. Do not call the trusted function from a browser client.

On an isolated staging tenant, temporarily delete one counter row inside a transaction, call the allocator and confirm failure, then roll back that transaction. Do not run that missing-row exercise on production.

**Gaps and non-reuse:** Allocate once in staging and commit without inserting a document, then allocate again; the second number must be greater and the stored `last_number` must equal it. Create and delete an old staging sale or purchase, then allocate again; the next value must exceed the deleted document's invoice number. Check that no duplicate string was returned within the tenant/type. Use an isolated staging tenant to advance `last_number` to 9999 only for the formatting test, then confirm the next result is `SAL-10000` or `PUR-10000` and the stored value is 10000.

## Recovery

If migration fails before `COMMIT`, PostgreSQL rolls it back; resolve the reported data issue and retry while writes stay paused. If migration succeeds but the application rollout fails, keep creation paused or continue using a version that calls the allocator. Do not roll back to the count-based routes while writes are enabled. Keep `invoice_counters` and its highest values after any issued number. Never decrement or reseed from surviving document counts; deleted documents and failed inserts can leave deliberate gaps. A future schema rollback must preserve counter history before removing any database objects.
